# 기능 요구사항 기준선

> 2026-07 React 마이그레이션에서 `FR-*`를 React route로 옮겼다. `OBS-*`는 기존 정적 구현에서 확인된 결함 기록이며 React 구현에서는 안전한 CSRF 처리, 입력 검증, 댓글 대상/count 동기화 등으로 의도적으로 수정했다.

## 1. 목적과 해석 원칙

이 문서는 현재 HTML/JavaScript에서 관찰되는 기능을 리팩터링 전 기준선으로 고정한다. `FR-*`는 보존할 사용자 기능, `OBS-*`는 현재 구현의 특성 또는 불일치다. `OBS-*`는 무심코 수정하지 말고, 제품 결정을 거쳐 요구사항과 함께 변경한다.

서비스 이름은 **뮤직피디아**이며, 사용자가 음악 감상 경험과 관련 정보를 게시글과 댓글로 기록하고 토론하는 음악 커뮤니티를 지향한다. 정보 구조와 사용 흐름은 일반적인 커뮤니티의 피드·상세·작성 형식을 따른다. 위키백과와 Reddit은 serif 로고, 파란 링크, 절제된 색상 등 시각 표현에만 참고하며 특정 서비스의 정보 구조, 로고 또는 상표를 복제하지 않는다. 콘텐츠 구분에는 닫힌 테두리나 세로선을 지양하고 여백과 가로선을 우선 사용한다.

공통 전제는 다음과 같다.

- 모든 API 요청은 쿠키 세션을 전달하기 위해 `credentials: "include"`를 사용한다.
- 페이지 진입 시 `/csrf`를 조회하며, 상태 변경 요청 대부분은 `XSRF-TOKEN` 쿠키 값을 `X-XSRF-TOKEN` 헤더로 보낸다.
- 상단 프로필 버튼은 `localStorage.user_profileImageUrl`을 표시한다.
- 프로필 메뉴는 버튼 클릭으로 열고 닫으며, 메뉴 밖 클릭 시 닫힌다.
- 로그아웃 성공 시 local/session storage를 모두 비우고 로그인 화면으로 이동한다.

## 2. 인증과 회원가입

### FR-AUTH-01 로그인 입력 검증

- 이메일은 필수이며 `문자열@문자열.문자열` 형태여야 한다.
- 비밀번호는 8~20자이며 영문 대문자, 영문 소문자, 숫자, 특수문자를 각각 하나 이상 포함해야 한다.
- 두 필드가 모두 유효할 때만 로그인 버튼을 활성화한다.
- 로그인 실패 응답이 HTTP 302이면 비밀번호 영역에 아이디/비밀번호 확인 메시지를 표시한다.

### FR-AUTH-02 로그인 성공

- 로그인 폼을 multipart `FormData`로 제출한다.
- 성공 후 `/csrf`를 다시 호출하고 응답의 사용자 ID, 이메일, 닉네임, 프로필 이미지 경로를 local storage에 저장한다.
- 저장 후 게시글 목록으로 이동한다.

### FR-AUTH-03 회원가입

- 프로필 이미지, 이메일, 비밀번호, 비밀번호 확인, 닉네임을 검증하며 전부 통과할 때만 제출 버튼을 활성화한다.
- 이메일은 로그인과 같은 형식이며 서버 중복 검사 결과가 고유해야 한다.
- 비밀번호 정책은 로그인과 같고 확인 값과 일치해야 한다.
- 닉네임은 필수, 공백 없음, 최대 10자이며 서버 중복 검사 결과가 고유해야 한다.
- 프로필 이미지는 먼저 업로드하고 반환된 URL을 가입 폼의 `profileImageUrl`로 전달한다.
- 가입 성공 시 로그인 화면으로 이동한다.

## 3. 게시글

### FR-POST-01 목록과 무한 스크롤

- 최초 진입 시 `page=0` 게시글 목록을 요청한다.
- 문서 하단 100px 이내로 스크롤할 때 page를 1 증가시키고 다음 목록을 뒤에 추가한다.
- 각 카드에는 최대 26자로 잘린 제목, 댓글/조회수, 작성 시각, 작성자 프로필과 닉네임을 표시한다.
- 카드를 선택하면 해당 `postId`의 상세 화면으로 이동한다.

### FR-POST-02 작성

- 제목은 필수이고 HTML 입력 기준 최대 26자다. 내용도 필수다.
- 제품 요구사항은 제목과 내용이 유효할 때만 완료 버튼을 활성화하는 것이다. 현재 코드는 내용 상태가 `true`로 시작하여 제목만 blur하면 버튼이 활성화될 수 있다(OBS-11).
- 첨부 이미지는 별도 업로드 후 반환 URL을 게시글 폼에 포함한다.
- 생성 성공 시 응답의 `postId`에 해당하는 상세 화면으로 이동하고, 401이면 로그인 화면으로 이동한다.

### FR-POST-03 상세

- URL query의 `postId`로 상세와 댓글 목록을 조회한다.
- 제목, 작성자, 프로필, 작성 시각, 본문, 이미지를 표시한다.
- 조회수/댓글 수는 1,000 미만이면 원 숫자, 이상이면 1,000으로 나눈 값에 `K`를 붙인다.
- 상세 데이터의 ID/제목/본문/이미지 URL은 수정 화면 전달을 위해 local storage에 저장한다.
- 상세 조회가 401이면 로그인 화면으로 이동한다.

### FR-POST-04 수정·삭제

- 수정 화면은 local storage의 기존 제목/본문/이미지를 채우고, 성공 시 상세 화면으로 돌아간다.
- 삭제 버튼은 확인 모달을 열고 배경 스크롤을 막는다. 취소하면 모달을 닫고 스크롤을 복구한다.
- 삭제 확인 성공 시 목록 화면으로 이동한다.

## 4. 댓글

### FR-COMMENT-01 조회와 작성

- 상세 화면 진입 시 댓글을 조회하여 작성자 프로필/닉네임, 작성 시각, 내용을 순서대로 표시한다.
- 빈 댓글은 등록 버튼을 비활성화한다.
- 등록 성공 시 반환된 댓글을 목록 끝에 추가하고 댓글 수를 1 증가시키며 입력을 비운다.

### FR-COMMENT-02 수정과 삭제

- 수정 선택 시 일반 작성 폼을 숨기고 수정 폼을 표시하며 기존 내용을 채운다. 대상 댓글은 수정 중 숨긴다.
- 수정 성공 시 해당 댓글 내용을 교체하고 댓글/폼을 원래 상태로 복구한다.
- 삭제 선택 시 확인 모달을 표시한다. 삭제 성공 시 DOM에서 댓글을 제거하고 모달을 닫는다.

## 5. 회원 관리

### FR-USER-01 회원정보 수정

- 화면 진입 시 local storage의 이메일, 닉네임, 프로필 이미지를 표시한다.
- 닉네임은 필수이고 최대 10자이며 서버 중복 검사를 통과해야 한다.
- 프로필 이미지를 업로드하면 미리보기와 폼의 URL을 갱신한다.
- 수정 성공 시 닉네임/프로필 URL을 local storage에 반영하고 5초 동안 완료 toast를 표시한다.

### FR-USER-02 비밀번호 변경

- 새 비밀번호는 8~20자이며 대문자, 소문자, 숫자, 특수문자를 각각 하나 이상 포함해야 한다.
- 확인 값과 일치할 때만 수정 버튼을 활성화한다.
- 성공 시 완료 toast를 5초 동안 표시한다.

### FR-USER-03 회원 탈퇴

- 회원 탈퇴 선택 시 확인 모달을 표시하고 취소할 수 있다.
- 확인 후 삭제 성공 시 로그인 화면으로 이동한다.

## 6. 리팩터링 인수 조건

최소한 다음 시나리오를 자동화한 후 구조를 변경한다.

1. 유효/무효 이메일 및 비밀번호 조합에 따른 로그인 버튼과 helper text를 검증한다.
2. 회원가입의 모든 검증 상태(빈 값, 형식, 불일치, 공백, 길이, 중복)를 검증한다.
3. 페이지 0 로드 후 하단 스크롤에서 page 1 결과가 중복 없이 append되는지 검증한다.
4. 게시글 작성 → 상세 → 수정 → 삭제의 화면 이동과 요청 payload를 검증한다.
5. 상세 조회의 표시 값과 999/1000 카운트 formatting을 검증한다.
6. 댓글 작성/수정/삭제의 DOM 변화와 댓글 수 변화를 검증한다.
7. 프로필 변경 후 header와 local storage가 일치하는지 검증한다.
8. 로그아웃 후 두 storage가 비고 로그인 화면으로 이동하는지 검증한다.
9. 모든 상태 변경 요청의 쿠키 전송 및 CSRF header를 검증한다.

## 7. 현재 구현상 주의점

- **OBS-01:** API origin이 `127.0.0.1`과 `localhost`로 혼용된다. 브라우저의 쿠키/origin 관점에서는 서로 다를 수 있다.
- **OBS-02:** `getCSRFToken()`은 쿠키가 없으면 `.split()` 호출에서 예외가 발생할 수 있다.
- **OBS-03:** 목록 무한 스크롤에는 중복 요청 방지, 마지막 페이지 판단, 오류 복구가 없다.
- **OBS-04:** 댓글 삭제 대상 ID는 수정 버튼을 누를 때만 session storage에 기록되므로, 삭제만 바로 누르면 잘못된 대상을 사용할 가능성이 있다.
- **OBS-05:** 댓글 삭제 시 표시 댓글 수를 감소시키지 않는다.
- **OBS-06:** 회원정보 수정의 `validateNickname()`은 async지만 submit handler에서 await하지 않는다. 현재 조건문은 Promise를 검사하므로 의도한 차단과 다를 수 있다.
- **OBS-07:** 회원정보 변경/탈퇴 요청과 비밀번호 변경 요청은 다른 상태 변경 요청과 달리 CSRF header를 명시하지 않는다.
- **OBS-08:** 게시글 수정 화면은 URL의 `postId`보다 local storage에 마지막으로 본 게시글 정보를 사용한다.
- **OBS-09:** HTML/스크립트에는 성공 응답만 처리하고 오류 상태에서는 아무 동작도 하지 않는 분기가 다수 있다.
- **OBS-10:** 게시글 신고 코드는 주석 처리되어 있어 제공 기능이 아니다.
- **OBS-11:** 게시글 작성의 content 검증 초기값이 `true`이고 검증은 blur에서만 일어나므로, 빈 본문인데도 제출 버튼이 활성화될 수 있다.
- **OBS-12:** 로그인에서 유효했던 비밀번호를 무효 값으로 바꾸면 상태는 false가 되지만 버튼 활성 조건을 다시 계산하지 않아 활성 상태가 남을 수 있다.
- **OBS-13:** 회원가입의 프로필 파일 검사는 FileList를 빈 문자열과 비교하므로 change 이후 파일 존재를 정확히 표현하지 못하며 helper renderer도 호출되지 않는다.
- **OBS-14:** 상세 및 댓글 markup은 API 문자열을 `innerHTML` template에 직접 삽입한다. React 전환 시 기본 escaping을 해제하지 말고 표시 결과와 XSS 안전성을 함께 테스트한다.
- **OBS-15:** 비밀번호 변경 화면은 다른 인증 후 화면과 달리 페이지 진입 `/csrf` 호출을 하지 않는다.

이 항목들은 현재 동작을 정확히 이해하기 위한 기록이지 권장 설계가 아니다. 수정할 때는 기대 동작을 결정하고 해당 인수 조건을 먼저 추가한다.
