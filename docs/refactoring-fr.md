# 프론트엔드 인증 상태 관리 리팩토링 요구사항

## 1. 리팩토링 목적

현재 프론트엔드에서 사용자 인증 상태, 세션 만료, CSRF 토큰, 로그아웃 및 회원 탈퇴 흐름을 일관된 방식으로 관리할 수 있도록 인증 관련 구조를 리팩토링한다.

이번 리팩토링의 주요 목표는 다음과 같다.

* 사용자 인증 상태를 전역에서 일관되게 관리한다.
* 페이지 이동마다 불필요하게 현재 사용자 정보를 요청하지 않는다.
* 세션 만료를 프론트엔드가 감지하고 즉시 인증 상태를 초기화한다.
* 인증 실패, 권한 부족, CSRF 실패를 구분하여 처리한다.
* 로그아웃과 회원 탈퇴 시 서버와 프론트엔드의 인증 정보를 함께 정리한다.
* 개별 컴포넌트가 인증 및 CSRF 처리 방식을 직접 구현하지 않도록 공통화한다.

---

# 2. 인증 상태 모델

## 2.1 인증 상태 구분

프론트엔드는 인증 상태를 다음 세 가지로 구분해야 한다.

```text
unknown
authenticated
anonymous
```

각 상태의 의미는 다음과 같다.

### `unknown`

아직 백엔드에 현재 로그인 상태를 확인하지 않은 상태이다.

애플리케이션 최초 실행이나 브라우저 새로고침 직후의 초기 상태로 사용한다.

### `authenticated`

백엔드의 `/users/me` 요청을 통해 로그인된 사용자임을 확인한 상태이다.

이 상태에서는 사용자 정보 객체가 존재해야 한다.

### `anonymous`

백엔드의 `/users/me` 요청 결과 현재 로그인된 사용자가 없다고 확인된 상태이다.

이 상태에서는 사용자 정보 객체가 존재하지 않아야 한다.

---

## 2.2 인증 상태 객체

인증 상태는 전역 상태로 관리한다.

최소한 다음 정보를 포함해야 한다.

```typescript
type AuthStatus = 'unknown' | 'authenticated' | 'anonymous';

interface AuthState {
    status: AuthStatus;
    user: User | null;
}
```

다음 불변 조건을 유지해야 한다.

```text
status === 'authenticated' → user !== null
status === 'anonymous'     → user === null
status === 'unknown'       → user === null
```

단순히 `user === null`인지만 확인해서는 안 된다.

`user === null`은 다음 두 상태를 모두 의미할 수 있기 때문이다.

* 아직 로그인 상태를 확인하지 않은 상태
* 확인 결과 익명 사용자로 판정된 상태

인증 상태를 구분하지 않으면 익명 사용자가 페이지를 이동할 때마다 `/users/me` 요청을 반복할 가능성이 있다.

---

# 3. 현재 사용자 조회

## 3.1 `/users/me` 호출 조건

프론트엔드는 인증 상태가 `unknown`일 때만 `/users/me`를 호출한다.

```text
auth.status === unknown
        ↓
GET /users/me
```

이미 인증 상태가 `authenticated` 또는 `anonymous`로 확인된 경우에는 페이지를 이동할 때마다 `/users/me`를 다시 호출하지 않는다.

단, 브라우저 새로고침으로 프론트엔드 메모리 상태가 초기화되면 인증 상태가 다시 `unknown`이 되므로 `/users/me`를 호출해야 한다.

---

## 3.2 `/users/me` 응답 처리

백엔드는 현재 사용자의 인증 여부에 따라 다음과 같이 응답한다고 가정한다.

### 인증된 사용자

```http
200 OK
```

```json
{
  "id": 1,
  "nickname": "user",
  "profileImageUrl": "/files/profile/1"
}
```

프론트엔드는 다음 상태로 변경한다.

```text
status = authenticated
user = 응답받은 사용자 객체
```

### 익명 사용자 또는 만료된 세션

```http
401 Unauthorized
```

프론트엔드는 다음 상태로 변경한다.

```text
status = anonymous
user = null
```

---

## 3.3 중복 요청 방지

여러 컴포넌트나 페이지가 동시에 사용자 정보 조회를 요청하더라도 `/users/me` 요청이 중복 실행되지 않도록 해야 한다.

현재 조회 중인 Promise를 공유하는 등의 방식으로 중복 요청을 방지한다.

예시 구조:

```typescript
let currentUserRequest: Promise<User | null> | null = null;

async function initializeAuth() {
    if (authState.status !== 'unknown') {
        return authState;
    }

    if (currentUserRequest) {
        return currentUserRequest;
    }

    currentUserRequest = fetchCurrentUser();

    try {
        return await currentUserRequest;
    } finally {
        currentUserRequest = null;
    }
}
```

구체적인 구현 방식은 현재 프로젝트 구조에 맞게 결정한다.

---

# 4. HTTP 요청 공통 처리

## 4.1 공통 API 클라이언트 도입

각 컴포넌트에서 직접 `fetch`를 호출하면서 인증 오류와 CSRF 토큰을 개별 처리하지 않도록 공통 API 요청 함수를 구성한다.

예시:

```typescript
apiFetch(url, options)
```

공통 API 요청 함수는 다음 책임을 가진다.

* 백엔드 요청에 필요한 공통 옵션 설정
* 쿠키 포함 설정
* 상태 변경 요청에 대한 CSRF 토큰 처리
* 응답 상태 코드 공통 처리
* 세션 만료 감지
* 인증 상태 초기화
* 필요한 경우 공통 예외 객체 생성

---

## 4.2 쿠키 포함

세션 기반 인증을 사용하므로 백엔드 요청에는 쿠키가 포함되어야 한다.

프론트와 백엔드의 Origin이 다른 경우 다음 옵션을 사용한다.

```typescript
credentials: 'include'
```

모든 백엔드 API 요청이 공통 API 클라이언트를 거치도록 하여 `credentials` 설정이 누락되지 않게 한다.

---

# 5. 인증 및 세션 만료 처리

## 5.1 인증 검사가 발생하는 요청

인증과 인가는 HTTP 메서드 자체가 아니라 백엔드의 보안 정책에 따라 수행된다.

따라서 다음 요청은 모두 인증 검사의 대상이 될 수 있다.

```text
GET
POST
PUT
PATCH
DELETE
```

예를 들어 다음 GET 요청도 인증이 필요하다.

```text
GET /users/me
GET /admin/users
GET /posts/drafts
```

POST, PUT, PATCH, DELETE 요청에만 인증 검사가 발생한다고 가정하지 않는다.

---

## 5.2 `401 Unauthorized` 처리

백엔드가 `401 Unauthorized`를 반환하면 다음 중 하나로 판단한다.

* 로그인되지 않은 사용자
* 세션 만료
* 유효하지 않은 세션
* 인증 정보가 제거된 상태

공통 API 클라이언트는 `401` 응답을 받으면 프론트엔드 인증 상태를 즉시 초기화한다.

```text
status = anonymous
user = null
CSRF 관련 메모리 상태 초기화
```

필요한 경우 로그인 페이지로 이동시키거나 로그인 안내를 표시한다.

다만 `/users/me`처럼 익명 상태 확인을 목적으로 호출한 API에서는 `401`을 일반적인 익명 사용자 판정으로 처리할 수 있어야 한다.

---

## 5.3 `403 Forbidden` 처리

`403 Forbidden`을 세션 만료로 간주해서는 안 된다.

`403`은 다음과 같은 상황에서 발생할 수 있다.

* 로그인은 되어 있지만 권한이 부족함
* 관리자 전용 API에 일반 사용자가 접근함
* CSRF 토큰이 누락됨
* CSRF 토큰이 일치하지 않음
* 접근 정책에 의해 요청이 거절됨

따라서 `403` 응답을 받았다는 이유만으로 사용자 객체를 폐기하거나 익명 사용자로 변경하지 않는다.

`401`과 `403`을 반드시 구분한다.

```text
401 → 인증 상태 초기화
403 → 권한 또는 CSRF 오류 처리
```

---

## 5.4 리다이렉션 응답 방지 전제

프론트엔드와 백엔드가 분리된 API 환경에서는 인증 실패가 로그인 HTML 페이지로 리다이렉트되지 않아야 한다.

백엔드는 다음 응답을 명시적으로 반환하는 것을 전제로 한다.

```text
인증 실패 또는 세션 만료 → 401
권한 부족 또는 접근 거부 → 403
```

프론트엔드는 `302` 리다이렉션 응답을 인증 실패 판정 방식으로 사용하지 않는다.

---

# 6. CSRF 토큰 관리

## 6.1 CSRF 검사 대상

CSRF 검사는 일반적으로 서버 상태를 변경하는 요청에 적용된다.

```text
POST
PUT
PATCH
DELETE
```

GET 요청은 서버 상태를 변경하지 않도록 구성하며, 일반적으로 CSRF 검사의 대상에서 제외한다.

---

## 6.2 CSRF 토큰 조회

상태 변경 요청을 보내기 전에 유효한 CSRF 토큰이 필요하다.

공통 API 클라이언트 또는 별도의 CSRF 관리 모듈이 다음 책임을 가진다.

* 현재 CSRF 토큰 존재 여부 확인
* 필요한 경우 `/csrf` 호출
* 응답받은 CSRF 토큰 저장
* 상태 변경 요청 헤더에 CSRF 토큰 추가
* 동시에 여러 요청이 발생했을 때 `/csrf` 중복 호출 방지

예시 헤더:

```http
X-XSRF-TOKEN: csrf-token
```

실제 쿠키 및 헤더 이름은 현재 백엔드 설정을 기준으로 사용한다.

---

## 6.3 CSRF 토큰과 인증 상태의 관계

CSRF 토큰이 존재한다고 해서 로그인된 상태인 것은 아니다.

CSRF 토큰은 요청 위조 방지를 위한 값이며, 사용자 인증 여부는 세션과 `Authentication`을 통해 결정된다.

따라서 다음 값을 서로 다른 상태로 관리한다.

```text
사용자 인증 상태
CSRF 토큰 상태
```

---

## 6.4 CSRF 오류 처리

CSRF 검증 실패는 일반적으로 `403 Forbidden`으로 반환될 수 있다.

CSRF 실패가 발생했을 때 사용자 인증 상태를 즉시 익명으로 변경하지 않는다.

프론트엔드는 다음과 같은 처리를 할 수 있다.

1. 기존 CSRF 토큰을 폐기한다.
2. `/csrf`를 다시 호출하여 새 토큰을 발급받는다.
3. 안전하게 재시도 가능한 요청인 경우 한 번만 재시도한다.
4. 재시도에도 실패하면 사용자에게 오류를 알린다.

무한 재시도가 발생하지 않도록 요청별 재시도 횟수를 제한해야 한다.

파일 업로드나 중복 실행 위험이 있는 요청은 자동 재시도 여부를 신중히 결정한다.

---

## 6.5 CSRF 토큰 폐기

로그아웃, 회원 탈퇴 또는 세션 만료가 확인되면 프론트엔드가 메모리에 저장한 CSRF 토큰을 폐기한다.

```text
csrfToken = null
```

CSRF 토큰 쿠키가 JavaScript에서 접근 가능한 경우 프론트엔드에서 삭제할 수도 있지만, 쿠키의 최종 정리 책임은 백엔드 로그아웃 처리에 두는 것을 원칙으로 한다.

프론트엔드에서 쿠키를 직접 삭제하려면 기존 쿠키와 동일한 `Path`와 `Domain`을 사용해야 하므로, 가능하면 백엔드가 쿠키를 삭제하도록 한다.

---

# 7. `JSESSIONID` 관리

## 7.1 프론트엔드 직접 접근 금지

`JSESSIONID` 쿠키는 `HttpOnly`로 설정되어 있으므로 JavaScript에서 읽거나 수정하거나 삭제하지 않는다.

다음과 같은 처리를 시도하지 않는다.

```typescript
document.cookie에서 JSESSIONID 조회
document.cookie를 이용한 JSESSIONID 삭제
로컬 스토리지에 JSESSIONID 복사
```

브라우저는 백엔드 요청 시 `JSESSIONID`를 자동으로 포함한다.

---

## 7.2 세션 폐기 책임

세션 무효화와 `JSESSIONID` 폐기는 백엔드가 담당한다.

로그아웃 및 회원 탈퇴 성공 시 백엔드는 다음 작업을 수행해야 한다.

* 서버 세션 무효화
* `SecurityContext` 제거
* 인증 정보 제거
* `JSESSIONID` 쿠키 만료
* CSRF 토큰 저장소 정리
* 필요한 경우 CSRF 쿠키 만료

프론트엔드는 응답 성공 후 내부 인증 상태를 초기화한다.

---

# 8. 로그아웃 처리

## 8.1 로그아웃 요청

로그아웃은 백엔드 로그아웃 API를 통해 수행한다.

예시:

```http
POST /logout
```

로그아웃 요청 자체가 CSRF 보호 대상이라면 유효한 CSRF 토큰을 포함해야 한다.

---

## 8.2 로그아웃 성공 처리

백엔드 로그아웃 성공 후 프론트엔드는 다음 상태 초기화 함수를 호출한다.

```typescript
clearAuthState()
```

해당 함수는 최소한 다음 작업을 수행한다.

```text
auth.status = anonymous
auth.user = null
메모리의 CSRF 토큰 제거
사용자별 캐시 제거
사용자 권한 정보 제거
사용자 전용 페이지 상태 제거
```

로그아웃 후 인증이 필요한 페이지에 머물러 있다면 공개 페이지 또는 로그인 페이지로 이동한다.

---

## 8.3 로그아웃 실패 처리

로그아웃 API 요청이 네트워크 오류로 실패한 경우 서버 세션이 실제로 무효화되지 않았을 가능성이 있다.

따라서 단순히 프론트 상태만 초기화하고 로그아웃이 성공했다고 처리하지 않는다.

사용자에게 로그아웃 실패를 알리거나 `/users/me`를 다시 호출해 최종 인증 상태를 확인할 수 있도록 한다.

단, 백엔드가 이미 `401`을 반환했다면 현재 세션이 유효하지 않은 상태이므로 프론트 인증 상태를 익명으로 초기화한다.

---

# 9. 회원 탈퇴 처리

## 9.1 처리 순서

회원 탈퇴 전에 로그아웃을 먼저 수행해서는 안 된다.

로그아웃을 먼저 하면 서버가 현재 요청 사용자의 신원을 확인할 인증 정보를 잃게 된다.

회원 탈퇴는 다음 순서로 처리한다.

```text
1. 인증된 상태에서 회원 탈퇴 요청
2. 백엔드가 현재 사용자의 인증 정보 확인
3. 필요한 경우 비밀번호 또는 추가 인증 확인
4. 회원 탈퇴 처리
5. 탈퇴 성공 후 서버 세션 무효화
6. JSESSIONID와 CSRF 토큰 정리
7. 프론트엔드 인증 상태 초기화
```

---

## 9.2 회원 탈퇴 API

예시:

```http
DELETE /users/me
```

회원 탈퇴 요청에는 현재 로그인된 사용자의 세션과 CSRF 토큰이 포함되어야 한다.

프론트엔드가 사용자 ID를 임의로 전달하여 탈퇴 대상을 정하지 않는다.

백엔드는 세션의 `Authentication`을 기준으로 현재 탈퇴 대상 사용자를 결정한다.

---

## 9.3 탈퇴 성공 처리

회원 탈퇴가 성공하면 로그아웃이 함께 완료된 것으로 처리한다.

프론트엔드는 다음 상태를 초기화한다.

```text
auth.status = anonymous
auth.user = null
CSRF 토큰 초기화
사용자 전용 캐시 제거
프로필 및 권한 데이터 제거
```

이후 공개 메인 페이지 또는 탈퇴 완료 페이지로 이동한다.

---

## 9.4 탈퇴 실패 처리

회원 탈퇴에 실패한 경우 프론트엔드 인증 상태를 임의로 제거하지 않는다.

예를 들어 다음과 같은 오류가 발생할 수 있다.

* 비밀번호 불일치
* 서버 내부 오류
* 탈퇴 정책 위반
* 관련 데이터 처리 실패

탈퇴가 실패했는데 로그아웃만 완료되는 상태를 만들지 않아야 한다.

---

# 10. 사용자 정보 변경 처리

프로필 수정, 닉네임 변경, 프로필 이미지 변경 등 현재 사용자 정보가 변경되는 API가 성공하면 전역 사용자 상태를 갱신한다.

가능한 방식은 다음 중 하나를 선택한다.

### 응답 객체로 즉시 갱신

백엔드가 변경된 사용자 객체를 반환하면 해당 값으로 `auth.user`를 갱신한다.

```text
PUT /users/me 성공
        ↓
응답 사용자 객체로 auth.user 갱신
```

### `/users/me` 재조회

변경 API가 사용자 정보를 반환하지 않으면 인증 상태를 `unknown`으로 되돌리지 말고, 현재 사용자 정보만 명시적으로 다시 조회한다.

```text
프로필 변경 성공
        ↓
GET /users/me
        ↓
auth.user 갱신
```

프로필 이미지 URL이 변경됐을 경우 브라우저 캐시로 이전 이미지가 표시되지 않도록 필요한 경우 버전 쿼리 또는 변경된 URL을 사용한다.

---

# 11. 인증이 필요한 페이지 처리

인증이 필요한 페이지는 인증 상태가 `unknown`인 동안 바로 로그인 페이지로 이동시키지 않는다.

다음 순서로 처리한다.

```text
unknown
   ↓
인증 상태 초기화 요청
   ↓
authenticated → 페이지 표시
anonymous     → 로그인 페이지 또는 접근 불가 화면
```

`unknown` 상태에서는 로딩 UI를 표시한다.

인증 상태 확인이 끝나기 전에 `user === null`이라는 이유만으로 로그인 페이지로 이동하지 않는다.

---

# 12. 익명 사용자 페이지 처리

익명 사용자도 접근할 수 있는 페이지에서는 `/users/me`의 `401`을 일반적인 오류 화면으로 표시하지 않는다.

해당 응답은 단순히 다음 상태를 의미한다.

```text
현재 로그인된 사용자가 없음
```

익명 사용자에게도 필요한 공개 콘텐츠는 정상적으로 렌더링한다.

---

# 13. 오류 처리 구조

공통 API 클라이언트는 응답 오류를 다음 범주로 구분할 수 있어야 한다.

```text
AuthenticationError
AuthorizationError
CsrfError
ValidationError
NotFoundError
ServerError
NetworkError
```

최소한 다음 상태 코드를 구분한다.

```text
400 → 잘못된 요청 또는 검증 실패
401 → 인증되지 않음 또는 세션 만료
403 → 권한 부족 또는 CSRF 실패
404 → 리소스 없음
409 → 상태 충돌
500 이상 → 서버 오류
```

백엔드가 에러 코드 또는 에러 타입을 응답 본문에 제공한다면 HTTP 상태 코드와 함께 사용하여 `403`의 원인을 구분한다.

예시:

```json
{
  "code": "CSRF_TOKEN_INVALID",
  "message": "CSRF token is invalid."
}
```

```json
{
  "code": "ACCESS_DENIED",
  "message": "You do not have permission."
}
```

---

# 14. 프론트엔드 로깅

인증 관련 문제를 추적할 수 있도록 개발 환경에서 다음 이벤트를 로깅할 수 있다.

```text
AUTH_INITIALIZATION_STARTED
AUTH_INITIALIZATION_SUCCEEDED
AUTH_INITIALIZATION_ANONYMOUS
AUTH_SESSION_EXPIRED
AUTH_STATE_CLEARED
CSRF_TOKEN_REQUESTED
CSRF_TOKEN_REFRESHED
CSRF_REQUEST_RETRIED
LOGOUT_SUCCEEDED
LOGOUT_FAILED
WITHDRAWAL_SUCCEEDED
WITHDRAWAL_FAILED
```

다음 정보는 로그에 기록하지 않는다.

* `JSESSIONID` 전체 값
* CSRF 토큰 전체 값
* Cookie 헤더 전체
* 비밀번호
* Authorization 헤더
* 개인정보가 포함된 요청 본문 전체

운영 환경에서는 상세 로그를 제한하고, 필요한 이벤트와 오류 정보만 기록한다.

---

# 15. 테스트 요구사항

## 15.1 인증 상태 초기화 테스트

다음 시나리오를 검증한다.

* 초기 상태가 `unknown`이다.
* `/users/me`가 `200`이면 `authenticated`로 변경된다.
* `/users/me`가 `401`이면 `anonymous`로 변경된다.
* 여러 컴포넌트가 동시에 초기화를 요청해도 `/users/me`는 한 번만 호출된다.
* 이미 `authenticated` 또는 `anonymous`이면 불필요한 재조회가 발생하지 않는다.

---

## 15.2 세션 만료 테스트

다음 시나리오를 검증한다.

* 보호된 API가 `401`을 반환하면 사용자 상태가 초기화된다.
* `401` 발생 후 `auth.user`가 제거된다.
* 메모리의 CSRF 토큰이 제거된다.
* 로그인 필요 페이지에서 적절한 이동 또는 안내가 발생한다.

---

## 15.3 권한 부족 테스트

다음 시나리오를 검증한다.

* API가 `403`을 반환해도 사용자 상태는 유지된다.
* 일반 사용자가 관리자 API에 접근했을 때 로그아웃되지 않는다.
* 권한 부족 메시지가 표시된다.

---

## 15.4 CSRF 테스트

다음 시나리오를 검증한다.

* 상태 변경 요청에 CSRF 헤더가 포함된다.
* CSRF 토큰이 없으면 `/csrf`를 먼저 호출한다.
* 동시에 여러 상태 변경 요청이 발생해도 `/csrf` 요청이 중복되지 않는다.
* CSRF 실패 시 사용자 인증 상태가 제거되지 않는다.
* CSRF 토큰 갱신 후 재시도는 최대 한 번만 발생한다.
* 재시도 실패 시 무한 요청이 발생하지 않는다.

---

## 15.5 로그아웃 테스트

다음 시나리오를 검증한다.

* 로그아웃 성공 후 사용자 상태가 `anonymous`가 된다.
* 로그아웃 성공 후 사용자 객체와 CSRF 상태가 제거된다.
* 로그아웃 실패 시 성공한 것으로 표시하지 않는다.
* 이미 세션이 만료된 상태에서 로그아웃 API가 `401`을 반환하면 익명 상태로 정리된다.

---

## 15.6 회원 탈퇴 테스트

다음 시나리오를 검증한다.

* 로그아웃보다 회원 탈퇴 요청이 먼저 실행된다.
* 회원 탈퇴 성공 후 사용자 상태가 초기화된다.
* 탈퇴 요청에 세션 쿠키와 CSRF 토큰이 포함된다.
* 회원 탈퇴 실패 시 기존 로그인 상태가 유지된다.
* 탈퇴 실패 시 로그아웃 요청이 별도로 실행되지 않는다.

---

## 15.7 사용자 정보 변경 테스트

다음 시나리오를 검증한다.

* 프로필 수정 성공 후 전역 사용자 정보가 갱신된다.
* 프로필 이미지 수정 성공 후 새 이미지 URL이 반영된다.
* 사용자 정보 변경 실패 시 기존 전역 사용자 정보가 유지된다.
* 사용자 정보가 일부 누락됐다는 이유만으로 인증 상태가 익명으로 변경되지 않는다.

---

# 16. 권장 모듈 구조

현재 프로젝트 구조에 맞춰 이름은 조정할 수 있지만, 책임은 다음과 같이 분리한다.

```text
auth/
 ├─ auth-state
 ├─ auth-service
 ├─ csrf-service
 └─ auth-types

api/
 ├─ api-client
 ├─ api-error
 └─ response-handler
```

각 모듈의 책임은 다음과 같다.

## `auth-state`

* 현재 인증 상태 저장
* 사용자 정보 저장
* 인증 상태 변경 함수 제공
* 전체 인증 상태 초기화

## `auth-service`

* `/users/me` 호출
* 인증 초기화
* 로그인 성공 후 사용자 상태 갱신
* 로그아웃
* 회원 탈퇴 후 상태 정리

## `csrf-service`

* CSRF 토큰 조회
* CSRF 토큰 캐싱
* 동시 요청 중복 방지
* CSRF 토큰 초기화
* 필요한 경우 토큰 갱신

## `api-client`

* 공통 `fetch` 래퍼
* `credentials` 설정
* CSRF 헤더 설정
* HTTP 응답 상태 공통 처리
* `401` 발생 시 인증 상태 초기화
* API 오류 변환

---

# 17. 구현 시 주의사항

* 페이지 또는 컴포넌트마다 독립적으로 `/users/me`를 호출하지 않는다.
* `user === null`만으로 익명 사용자를 판단하지 않는다.
* 모든 `403` 응답에서 로그아웃시키지 않는다.
* `JSESSIONID`를 JavaScript에서 직접 관리하지 않는다.
* 세션 ID나 CSRF 토큰을 로컬 스토리지에 저장하지 않는다.
* CSRF 토큰과 사용자 인증 상태를 동일한 개념으로 취급하지 않는다.
* 로그아웃 전에 회원 탈퇴를 실행하지 않는다.
* 회원 탈퇴가 실패했는데 프론트 상태만 로그아웃 상태로 바꾸지 않는다.
* 인증 상태 확인이 끝나기 전 로그인 페이지로 리다이렉트하지 않는다.
* 상태 변경 요청의 CSRF 재시도는 무한 반복되지 않게 한다.
* 각 컴포넌트가 상태 코드별 인증 처리를 중복 구현하지 않게 한다.

---

# 18. 완료 조건

다음 조건이 충족되면 리팩토링이 완료된 것으로 판단한다.

1. 인증 상태가 `unknown`, `authenticated`, `anonymous`로 명확히 구분된다.
2. 애플리케이션 최초 실행 시에만 `/users/me`를 통한 인증 초기화가 수행된다.
3. 페이지 이동마다 `/users/me`가 반복 호출되지 않는다.
4. 모든 백엔드 API 요청이 공통 API 클라이언트를 통해 처리된다.
5. `401` 응답 시 프론트 인증 상태가 일관되게 초기화된다.
6. `403` 응답만으로 사용자가 로그아웃되지 않는다.
7. 상태 변경 요청에 CSRF 토큰이 일관되게 포함된다.
8. CSRF 토큰 조회 요청의 중복 실행이 방지된다.
9. 로그아웃 성공 시 세션 관련 프론트 상태가 모두 정리된다.
10. 회원 탈퇴는 인증된 상태에서 먼저 처리되고, 성공 후 로그아웃 상태로 전환된다.
11. 프로필 수정 후 전역 사용자 정보가 정상적으로 갱신된다.
12. 인증, 세션 만료, 권한 부족, CSRF 실패에 대한 테스트가 작성된다.
13. 세션 ID, CSRF 토큰, 비밀번호 등 민감한 값이 로그에 기록되지 않는다.
